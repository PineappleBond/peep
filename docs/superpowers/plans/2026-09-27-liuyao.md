## 数据流架构

### 端到端数据流

```mermaid
graph TD
    A[用户起卦] -->|输入 SixLines + 问题/背景/标签| B[LiuyaoCreateDialog]
    B -->|调用 buildChart(input)| C[core/chart.ts - buildChart]
    C -->|输出 ChartJSON + YongShen| D[saveLiuyaoRecord]
    D -->|IndexedDB 持久化| E[(liuyaoRecords 表)]
    E -->|listLiuyaoRecords| F[LiuyaoList]
    F -->|onSelect(record)| G[LiuyaoPage.selectedRecord]
    G -->|props| H[LiuyaoChart]
    G -->|divinationTime → buildLiuyaoHbarData| I[LiuyaoHbar]
    I -->|pick/visible 变化| J[vigorColumns 重算]
    J -->|props hbarState| H

    subgraph "旺衰列响应式更新"
        I -->|pick: {year, month, day, hour}| K[computeVigorColumns]
        K -->|8列 × 6爻 VigorState| H
    end
```

### 数据格式转换链

| 阶段      | 输入                               | 输出                            | 转换函数                   |
| --------- | ---------------------------------- | ------------------------------- | -------------------------- |
| 摇卦      | `Math.random()`                    | `SixLines` (6 个 0-3 值)        | `tossHexagram()`           |
| 排盘      | `ChartInput { lines, date }`       | `ChartJSON`                     | `buildChart()`             |
| 用神定位  | `ChartJSON + YongTarget`           | `YongShen`                      | `locateYong()`             |
| 持久化    | `ChartJSON + YongShen + 表单数据`  | `LiuyaoRecord`                  | 组装（LiuyaoCreateDialog） |
| hbar 构建 | `divinationTime + pick`            | `LiuyaoHbarData`                | `buildLiuyaoHbarData()`    |
| 旺衰计算  | `ChartJSON + visibleScopes + pick` | `VigorColumns` (8×6 VigorState) | `computeVigorColumns()`    |

### 关键设计决策：YongShen 存储

**问题**：`YongShen`（用神）数据是否存储在 `LiuyaoRecord` 中？

**决策**：**是**。理由：

1. `locateYong()` 依赖 `YongTarget`（用户选择的求测对象），这是用户输入，需要持久化
2. 避免每次选中记录都重新计算用神
3. 与 `ChartJSON` 一起存储保证数据完整性

**LiuyaoRecord 最终字段**：

```typescript
export interface LiuyaoRecord {
  id?: number;
  personId: number;
  divinationTime: string; // 起卦时间 ISO 格式
  question: string;
  background: string;
  note: string;
  tags: string[];
  lines: SixLines; // 六爻原始值（用于重新排盘验证）
  chart: ChartJSON; // 完整卦象
  yongTarget: YongTarget; // 求测对象（自占/父母/子女/配偶/兄弟/医药）
  yong: YongShen; // 用神定位结果
  savedAt: number;
}
```

> **注意**：`lines` 和 `chart` 存在一定冗余（`chart.lines` 已包含 `yang`/`moving` 信息），但保留 `lines` 是为了：
>
> 1. 调试 API 可直接用 `lines` 重新调用 `buildChart()` 验证一致性
> 2. 与大六壬的 `LiurenRecord.result` 模式保持一致（冗余存储换取可验证性）

## 状态管理架构

### 状态树

六爻页面的状态分为三层：

```
LiuyaoPage（页面级状态）
├── person: Person | null                    ← useDefaultPerson()
├── listRefreshKey: number                   ← useRefreshKey()
├── selectedRecord: LiuyaoRecord | null      ← useState
├── hbarState: LiuyaoHbarState               ← useState（六爻特有）
│   ├── visible: { yearly, monthly, daily, hourly }
│   └── pick: { year, month, day, hour }
├── dialogStates                             ← 4 个 useState (create/view/edit/delete)
│   ├── createDialogOpen, viewDialogOpen, ...
│   └── dialogRecord: LiuyaoRecord | null
├── debugApiRefs                             ← useRef (调试 API 用)
│   ├── createFormInitialDataRef
│   ├── createSubmitTrigger
│   ├── selectedRecordRef                    ← 镜像 selectedRecord
│   └── submitPollRef
│
├── LiuyaoList（列表子状态）
│   └── useListData 内部状态 (items, page, searchText, selectedTags, ...)
│
└── 派生数据（useMemo）
    ├── hbarData = buildLiuyaoHbarData(selectedRecord.divinationTime, hbarState.pick)
    └── vigorColumns = computeVigorColumns(selectedRecord.chart, hbarState.visible, hbarState.pick)
```

### hbar 状态管理方案

**方案选择：LiuyaoPage 内 useState（非 useReducer）**

理由：

1. 六爻 hbar 只有 4 级（yearly/monthly/daily/hourly），无大限、无童限，状态转换远比紫微简单
2. 紫微的 `pickReducer` 处理了 5 级 + lock/unlock + version 等复杂场景，六爻不需要
3. `visible` 和 `pick` 可以分别用两个 `useState` 管理，无需合并 reducer

```typescript
// LiuyaoPage.tsx 中的 hbar 状态
const [hbarVisible, setHbarVisible] = useState<LiuyaoHbarVisible>({
  yearly: true,
  monthly: true,
  daily: true,
  hourly: true,
});
const [hbarPick, setHbarPick] = useState<LiuyaoHbarPick>({
  year: divinationYear,
  month: divinationMonth,
  day: divinationDay,
  hour: divinationHour,
});

// 稳定化回调（避免 Row/Cell 组件不必要的重渲染）
const toggleYearly = useCallback(() => setHbarVisible(v => ({ ...v, yearly: !v.yearly })), []);
const toggleMonthly = useCallback(() => setHbarVisible(v => ({ ...v, monthly: !v.monthly })), []);
// ... daily, hourly 同理

const pickYear = useCallback((year: number) => setHbarPick(p => ({ ...p, year })), []);
const pickMonth = useCallback((month: number) => setHbarPick(p => ({ ...p, month })), []);
// ... day, hour 同理
```

### 派生数据计算与 memo 策略

```typescript
// 1. hbar 完整数据：仅在 selectedRecord 或 pick 变化时重算
const hbarData = useMemo(() => {
  if (!selectedRecord) return null;
  return buildLiuyaoHbarData(selectedRecord.divinationTime, hbarPick);
}, [selectedRecord?.divinationTime, hbarPick]);

// 2. 旺衰列数据：在 selectedRecord 或 visible 或 pick 变化时重算
const vigorColumns = useMemo(() => {
  if (!selectedRecord) return null;
  return computeVigorColumns(selectedRecord.chart, hbarVisible, hbarPick);
}, [selectedRecord?.chart, hbarVisible, hbarPick]);

// 3. 合并为 hbarState 传递给 LiuyaoChart（对象引用稳定化）
const hbarState = useMemo<LiuyaoHbarState>(
  () => ({
    visible: hbarVisible,
    pick: hbarPick,
  }),
  [hbarVisible, hbarPick],
);
```

### 切换 selectedRecord 时的 hbar 重置

当用户点击列表中不同记录时，`selectedRecord` 变化，需要重置 hbar pick 到新记录的起卦时间：

```typescript
const handleSelect = useCallback((record: LiuyaoRecord) => {
  setSelectedRecord(record);
  // 重置 hbar pick 到新记录的起卦时间
  const dt = new Date(record.divinationTime);
  setHbarPick({
    year: dt.getFullYear(),
    month: dt.getMonth() + 1,
    day: dt.getDate(),
    hour: /* 根据分钟推算时辰 */ 0,
  });
  // visible 保持不变（用户的显隐偏好是全局的）
}, []);
```

### 为什么不需要全局状态（zustand/context）

1. 六爻状态只在 `LiuyaoPage` 内使用，不需要跨页面共享
2. 与大六壬模式一致：页面级 `useState` + 子组件 `props` 传递
3. hbar/旺衰数据都是 `selectedRecord` 的派生数据，用 `useMemo` 即可
4. 列表内部状态由 `useListData` hook 管理，已封装良好

**Task 3.3：创建六爻旺衰列计算模块**

- 文件：`src/core/liuyao/vigorColumns.ts`
- 核心函数：

  ```typescript
  /**
   * 计算单个时间层级对 6 爻的旺衰。
   * @param chart - 完整卦象（从中提取每爻的五行）

   * @returns 6 个 VigorState，索引 0-5 对应爻位 1-6

  function computeLineVigors(chart: ChartJSON, timeBranch: Branch): VigorState[];

  /**
   * 计算完整旺衰列数据。
   *
   * 列结构（从左到右）：
   * 左侧 4 列（上级时间对 6 爻的影响）：
   *   [0] 太岁（年支）  → 对应 yearly visible
   *   [1] 流月（月建）  → 对应 monthly visible
   *   [2] 流日（日辰）  → 对应 daily visible
   *   [3] 流时（时支）  → 对应 hourly visible
   * 右侧 4 列（反向，镜像布局）：
   *   [4] 流时  [5] 流日  [6] 流月  [7] 太岁
   *
   * @param chart - 完整卦象
   * @param visible - 4 级可见性状态
   * @param pick - 当前选择的时间点（用于推算各级时间地支）
   * @returns 8 列，每列 6 个 VigorState；不可见列仍计算但 UI 隐藏
   */
  function computeVigorColumns(
    chart: ChartJSON,
    visible: LiuyaoHbarVisible,
    pick: LiuyaoHbarPick,
  ): VigorColumnData;
  ```

- **时间地支推算逻辑**：
  - 太岁（年支）：从 `pick.year` 推算，`BRANCHES[(year - 4) % 12]`
  - 月建：从 `pick.year + pick.month` 推算，使用 `monthBranch()` 函数（需从 `calendar.ts` 导入）
  - 日辰：从阳历日期推算，使用 `dayGanzhi()` 函数取地支部分
  - 时支：从 `pick.hour` 直接映射到地支索引

- **性能优化**：
  - 整个 `computeVigorColumns` 函数应通过调用方的 `useMemo` 实现 memo 化
  - 内部不做额外缓存（因为 useMemo 已保证输入不变时不重算）
  - 8 列中左右对称的列共享同一地支，计算结果可复用（太岁列和反向太岁列结果相同）

- **VigorColumnData 类型**：
  ```typescript
  type VigorColumnData = {
    /** 8 列的旺衰数据，索引 0-7 */
    columns: VigorState[][];
    /** 每列的地支标签（用于表头） */
    columnBranches: Branch[];
    /** 每列的角色标签（太岁/月建/日辰/时辰） */
    columnRoles: string[];
    /** 各级时间是否可见（从 hbarState.visible 透传） */
    visible: LiuyaoHbarVisible;
  };
  ```

## 性能优化方案

### Memo 化层次

| 层级              | 策略                      | 依赖                                  | 重算条件                         |
| ----------------- | ------------------------- | ------------------------------------- | -------------------------------- |
| `hbarData`        | `useMemo` in LiuyaoPage   | `divinationTime`, `hbarPick`          | 选中记录变化或 pick 变化         |
| `vigorColumns`    | `useMemo` in LiuyaoPage   | `chart`, `hbarVisible`, `hbarPick`    | 选中记录变化或 visible/pick 变化 |
| `LiuyaoChart`     | `React.memo`              | `record`, `hbarState`, `vigorColumns` | 三个 prop 的浅比较全部不变时跳过 |
| `LineRow`         | `React.memo` + 自定义比较 | 单爻数据                              | 该爻位的数据不变时跳过           |
| `VigorCell`       | `React.memo`              | `VigorState` 字符串                   | 旺衰状态不变时跳过               |
| `LiuyaoHbar.Row`  | `React.memo`              | `label`, `on`, `activeKey`, children  | 与 HoroscopeBar Row 策略一致     |
| `LiuyaoHbar.Cell` | `React.memo`              | `main`, `active`, `onClick`           | 与 HoroscopeBar Cell 策略一致    |

### 缓存策略

| 缓存项      | 类型     | maxSize | 键                     | 淘汰策略          |
| ----------- | -------- | ------- | ---------------------- | ----------------- |

| 流日列表    | LRUCache | 200     | "year-month"           | LRU               |

## 错误边界与降级策略

### 组件级错误边界

```typescript
// LiuyaoPage.tsx 中
<ErrorBoundary name="LiuyaoPage" maxAutoRetries={1}>
  <div className="liuyao-layout">
```

- `maxAutoRetries={1}`：自动重试 1 次，失败后展示降级 UI

### 数据加载失败降级

| 失败场景         | 降级策略                                                                 |
| ---------------- | ------------------------------------------------------------------------ |
| 默认人物加载失败 | `PageState` 展示 `initError`，提示"请刷新页面重试"（已有模式）           |
| 列表查询失败     | `useListData` 内部 catch → `loadError` 状态 → 展示"加载失败，请重试"按钮 |
| 单条记录读取失败 | `handleSelect` 中 catch → toast 提示，不更新 `selectedRecord`            |
| hbar 计算失败    | `buildLiuyaoHbarData` 返回 null → LiuyaoHbar 显示空状态                  |
| 旺衰列计算失败   | `computeVigorColumns` 降级为全"—"，不阻塞卦象展示                        |

### 排盘算法异常处理

```typescript
// LiuyaoCreateDialog.tsx 中
const handleSubmit = async () => {
  try {
    const chart = buildChart({ lines, date: divinationDate });
    const yong = locateYong(chart, yongTarget);
    const record: LiuyaoRecord = { /* ... */ chart, yong };
    await saveLiuyaoRecord(record);
    onSaved();
  } catch (err) {
    console.error("[LiuyaoCreateDialog] 排盘失败", err);
    setServerError(err instanceof Error ? err.message : "排盘失败，请检查输入");
  }
};
```

### 数据库操作失败回滚

- 使用 `createDbOperation("liuyaoDb")` 包装所有 DB 操作（与 `daliurenDb.ts` 一致）
- Dexie 事务自动保证原子性：`put` 失败不会写入部分数据
- 标签缓存在 `saveLiuyaoRecord` / `deleteLiuyaoRecord` 成功后才调用 `invalidateLiuyaoTagCache()`
- 如果 `invalidateLiuyaoTagCache()` 本身失败，仅 console.error，不影响主流程

## 风险与注意事项

### 风险 1：繁体转简体遗漏

- **风险等级**：中
- **缓解措施**：建立完整的繁简映射表，对所有移植文件做全文搜索替换，并用 grep 验证无遗漏繁体字
- **关键字符集**：`子孫→子孙`、`妻財→妻财`、`青龍→青龙`、`歸魂→归魂`、`遊魂→游魂`、`遯→遁`、`剝→剥`、`頤→颐`、`姤→姤`（不变）、`復→复`、`晉→晋`、`豐→丰`、`恆→恒`、`頤→颐`、`蠱→蛊`、`渙→涣`

### 风险 2：Hbar 逻辑与紫微差异大

- **风险等级**：高
- **说明**：紫微 hbar 依赖本命盘（Astrolabe），六爻以起卦时间为基准，两者计算逻辑完全不同
- **缓解措施**：不强行复用紫微 hbar，而是独立实现；但可复用 `buildMonths`、`buildDays`、`buildHours` 的底层函数（从 `src/core/hbar.ts` 导出），因为月/日/时的计算逻辑是通用的

### 风险 3：对称式表格的响应式布局

- **风险等级**：中
- **说明**：8 列 + 12 爻的对称表格在移动端可能过宽
- **缓解措施**：小屏幕下隐藏旺衰列，仅显示本卦/变卦核心信息；支持横向滚动

### 风险 4：IndexedDB 迁移兼容性

- **风险等级**：低
- **说明**：新增 v4 版本添加 liuyaoRecords 表
- **缓解措施**：遵循现有迁移模式（v2 加 liuren、v3 加 wiki），v4 加 liuyao，确保 upgrade 钩子正确

### 风险 5：核心算法正确性验证

- **风险等级**：高
- **说明**：排盘算法从老项目移植，需要验证简体版本与繁体版本的输出一致性
- **缓解措施**：编写对比测试，使用相同的输入参数，对比两版的 ChartJSON 输出

### 风险 6：hbar pick 与旺衰列的同步时序

- **风险等级**：中
- **说明**：用户快速连续点击 hbar 不同单元格时，`pick` 状态频繁变化可能导致旺衰列频繁重算，在低端设备上造成卡顿
- **缓解措施**：
  1. `computeVigorColumns` 的计算量很小（48 次查表），实测不太可能成为瓶颈
  2. 如果实测有问题，可在 `useMemo` 之前加 `useDeferredValue`（React 18）延迟旺衰列更新
  3. LiuyaoHbar 的 Row/Cell 已使用 memo，pick 变化不会导致整个 hbar 重渲染

### 风险 7：YongShen 存储格式的向前兼容

- **风险等级**：低
- **说明**：`YongShen.hidden` 包含 `stem`/`branch`/`elem` 字段，后续如果扩展用神分析（如元神/忌神/仇神链），可能需要修改存储结构
- **缓解措施**：
  1. Phase 1 暂不移植 `ShenChain` 相关类型（与计划一致）
  2. 后续扩展时通过 Dexie 版本升级（v5）做数据迁移
  3. `LiuyaoRecord` 中预留 `yongExtra?: Record<string, unknown>` 扩展字段（可选）
