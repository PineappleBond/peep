## 核心修复：消除 createConfirmHandler 自引用（TS7022）

### 问题根因

`createConfirmHandler` 的第一个参数需要接收 zodSchema，而部分 Function 文件在 Function 对象定义中直接引用了自身：

```typescript
// 错误写法（TS7022：隐式 any）
export const personCreateFunction = {
  zodSchema: z.object({...}),
  handler: createConfirmHandler(personCreateFunction.zodSchema, ...)  // ❌ 自引用
};
```

TypeScript 无法在 const 声明完成前推断其类型，导致隐式 `any`，进而引发连锁的 TS2339（属性不存在）错误。

### 解决方案

将 zodSchema 提取为独立常量，在 Function 对象声明之前定义：

```typescript
// 正确写法
const _personCreateSchema = z.object({...});
export const personCreateFunction = {
  zodSchema: _personCreateSchema,
  handler: createConfirmHandler(_personCreateSchema, ...)  // ✅ 无自引用
};
```

### 涉及文件与修复点

| 文件                   | 修复点                                                                 |
| ---------------------- | ---------------------------------------------------------------------- |
| `personFunctions.ts`   | `_personCreateSchema`、`_personUpdateSchema`、`_personDeleteSchema`    |
| `daliurenFunctions.ts` | `_daliurenCreateSchema`、`_daliurenDeleteSchema`（本轮清理未使用导入） |
| `liuyaoFunctions.ts`   | `_liuyaoCreateSchema`、`_liuyaoDeleteSchema`                           |
| `wikiFunctions.ts`     | `_wikiCreateSchema`、`_wikiUpdateSchema`                               |

总计消除 28+ 个 TS 编译错误。

## 次要优化

### 1. 清理 computed-key schema 工厂函数

`createUpdateTagsSchema`、`createUpdateNoteSchema`、`createBatchViewSchema` 三个共享工厂函数使用动态属性名（`[idFieldName]`），但 TypeScript 无法将 `{ [x: string]: ... }` 推断为具体的属性名类型（如 `{ recordId: number; tags: string[] }`），导致 handler 类型不匹配。

**决策**：删除这三个工厂函数，所有调用点改回内联 `z.object` 定义。

**根因**：这是 TypeScript 类型系统的固有限制——计算属性名无法产生窄类型。工厂函数虽然消除了代码重复，但引入了类型安全问题，得不偿失。

**保留的工厂函数**：`createListFiltersSchema` 仍然保留，因为它不使用计算属性名（只接受 `contextLabel: string` 参数，属性名固定），类型推断正常。

### 2. 删除 extractConfirmed 死代码

`extractConfirmed` 原本用于从已确认参数中去除 `confirmed` 字段，但 `createConfirmHandler` 内部已经使用解构赋值 `const { confirmed: _c, ...params } = input;` 完成了相同功能，因此 `extractConfirmed` 成为死代码。

**清理范围**：

- `src/core/rtcAgent/shared.ts`：删除函数定义
- `src/core/rtcAgent.ts`：从 re-export 中移除
- `src/core/rtcAgent.test.ts`：删除 import 及 6 个测试用例
- `src/core/rtcAgent/shared.test.ts`：删除 import 及 3 个测试用例

注：`needsConfirm` 仍然保留——`createConfirmHandler` 内部调用它构建确认响应对象。

### 3. 移除 lunar.ts 未使用导入

`lunar.ts` 导入了 `EightChar` 和 `LunarYear` 但从未使用（可能是早期重构遗留）。本轮移除。

### 4. 提取 pollUntil 通用轮询工具

`helpers.ts` 中的 `waitForPersonMatch`、`waitForPickReset`、`waitForPickMatch` 三个函数共享相同的轮询结构：

```typescript
// 重构前（每个函数都有这段）
const start = Date.now();
const maxIterations = Math.ceil(timeout / 20) + 10;
let iterations = 0;
while (++iterations <= maxIterations && Date.now() - start < timeout) {
  if (condition()) return;
  await new Promise(r => setTimeout(r, 20));
}
log("warn", "wait", "xxx等待超时", { timeout });
```

**提取为** `pollUntil(condition, options)`：

- 接受条件函数、超时、间隔、日志标签参数
- 内置最大迭代次数安全保护
- 返回 boolean 表示是否满足条件
- 超时自动记录 warn 日志

三个 `waitFor*` 函数重构后代码量减少约 60%，语义更清晰。

## 未本轮处理但值得关注的优化点

### TypeScript 推断限制导致的设计权衡

`createBatchViewSchema`、`createUpdateTagsSchema`、`createUpdateNoteSchema` 被删除是因为 TypeScript 无法推断计算属性名。如果需要恢复工厂模式，有两个选项：

1. **类型断言**：在工厂返回类型上 `as z.ZodObject<{ recordId: z.ZodNumber; tags: z.ZodArray<...> }>`，但引入了脆弱的类型断言。
2. **泛型参数**：让工厂接受类型参数而非属性名字符串，但增加了调用复杂度。

当前方案（内联 schema）虽然重复度略高，但类型安全且直观。这是 TypeScript 类型系统下的务实权衡。

### 其他候选优化

- `waitForStateUpdate`、`waitForAstrolabeStable` 有稳定性检查模式（连续 N 次采样相同），尚未提取为工厂——因为该模式仅在这两个函数中出现，抽象收益不大。
- DevDashboard.tsx、HoroscopeBar.tsx 等组件文件存在未使用导入，但属于前几轮范围之外的遗留问题。
